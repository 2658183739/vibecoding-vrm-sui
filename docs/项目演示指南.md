# 项目演示指南（详细版）

> 本文用于你在路演/答辩时稳定完成演示。按本文顺序操作，可在 5~8 分钟内完整覆盖核心能力。

## 一、演示目标

你需要让评委在短时间内看到三件事：
1. 这是一个真正可运行的产品，而不是概念代码。
2. 核心链上流程可闭环（出单、支付、赎回、结算）。
3. 项目满足比赛要求（Move 2024、官方 SDK、开源、AI 披露）。

## 二、演示前检查（建议提前 30 分钟完成）

### 1. 环境检查

```bash
pnpm install
pnpm build
pnpm test
pnpm dev
```

确认：
- 页面可打开：`http://localhost:5173`
- 钱包扩展可正常连接
- RPC 可访问（必要时准备备用 RPC）

### 2. 配置检查

核对 `apps/web/.env`：
- `VITE_PACKAGE_ID`、`VITE_MODULE_NAME`、`VITE_MERCHANT_ID`
- `VITE_STABLE_LAYER_STABLE_COIN_TYPE`、`VITE_STABLE_LAYER_USDC_TYPE`、`VITE_STABLE_LAYER_BRAND_USD_TYPE`
- `VITE_SUI_RPC_URL` 与网络一致

### 3. 资金检查

准备两个钱包：
- 商户钱包：有 gas，负责创建商品/账单
- 用户钱包：有 gas + USDC（用于 Mint+Pay）

### 4. 证据材料准备

提前打开这些文件页签：
- `packages/move/Move.toml`（展示 Move 2024）
- `ai-disclosure/tools.md`（展示 AI 披露）
- `docs/submission-checklist.md`（展示合规项）

## 三、推荐演示顺序（主线流程）

## 阶段 A：商户出单（约 1 分钟）

1. 打开 `/merchant`
2. 连接商户钱包
3. 创建 Product（输入标题与价格）
4. 基于 Product 创建 Invoice
5. 点击 invoice 跳转到 `/pay/:invoiceId`

你可以这样讲：
- “这里演示商户端最小闭环：先上架商品，再基于商品生成账单对象。”

评委关注点：
- 是否确实生成链上对象
- 是否可追踪 invoice objectId

## 阶段 B：用户支付（约 2 分钟）

### B1. 普通支付

1. 切换到用户钱包
2. 点击 `Pay`
3. 展示交易反馈卡片

重点展示字段：
- Digest
- Status
- Explorer 链接
- Receipt ObjectId（若解析到）

### B2. 一键支付（Mint+Pay）

1. 先展示页面中的“交易预览”（将 mint 多少、支付多少、使用哪些 USDC coin）
2. 点击 `Pay with USDC (Mint+Pay in one TX)`
3. 展示同样的反馈字段

你可以这样讲：
- “这一笔交易里先把 USDC 铸造成 BrandUSD，再立即调用支付合约完成付款。”

评委关注点：
- 是否真的是单笔交易
- 是否有明确交易结果和可复核链接

## 阶段 C：赎回与商户结算（约 2 分钟）

### C1. Redeem

1. 打开 `/redeem`
2. 展示 Banner：MVP 默认 T+1，Instant 作为 roadmap
3. 先演示 `Burn amount` 或 `Burn all`
4. 展示交易反馈

### C2. Claim + Metrics

1. 打开 `/merchant/claim`，执行 Claim
2. 打开 `/merchant/metrics`，点击 Refresh
3. 展示总供给与按币种供给

评委关注点：
- 功能是否分页面清晰可见
- 失败时是否有可读错误提示

## 阶段 D：Agent（约 1 分钟）

1. 打开右下角 Agent Drawer
2. 输入自然语言，例如“帮我支付这个账单”
3. 展示 Agent 返回的意图、步骤、动作按钮
4. 点击动作按钮触发钱包签名流程

评委关注点：
- Agent 是否真的可执行动作，而不是只聊天
- 用户是否仍保留签名控制权

## 四、失败兜底方案（非常重要）

### 1. RPC 抖动

现象：交易或读链超时。
处理：
- 立即切换备用 RPC
- 重试同一页面动作
- 明确说明“业务逻辑不依赖单点 RPC”

### 2. USDC 不足

现象：Mint+Pay 报余额不足。
处理：
- 先演示普通支付
- 或切换到准备好的用户钱包继续 Mint+Pay

### 3. Claim 权限不足

现象：Claim 失败。
处理：
- 展示错误提示区与可能原因
- 强调系统具备可解释失败反馈（不是静默失败）

## 五、评委常见问题回答模板

### Q1：你们如何满足 Move 2024 要求？
答：
- `packages/move/Move.toml` 使用 `edition = "2024.beta"`
- 合约 build/test 命令在文档中可复现

### Q2：是否使用官方 SDK？
答：
- 前端与 Agent 均使用官方 `@mysten/sui`
- 钱包签名通过官方 dApp kit 交互链路完成

### Q3：AI 参与了哪些部分？
答：
- 在 `ai-disclosure/` 中披露了工具、模型版本与 prompt 记录
- 敏感信息均打码

## 六、演示结束时必须强调

- 项目是完整可运行产品，不是单独合约或 PPT
- 关键流程可复核（digest + explorer）
- 仓库完整开源（合约 + 前端 + Agent + 文档 + AI 披露）

## 七、你上台前 60 秒复读清单

- 钱包是否已登录？
- `/merchant` 能否创建 invoice？
- `/pay` 是否能至少跑通一种支付？
- `/redeem`、`/merchant/claim`、`/merchant/metrics` 页面是否可打开？
- AI 披露文件是否可随时展示？

只要以上 5 项都通过，演示基本可控。
